## kernel-1 (CONFIRMED, minor)

`src/parameterized_tendencies/tagged_tracers/tagged_water.jl:356`

**Claim.** The kernel matches 11.1 and 11.2, but with the tableaux' negative explicit weights the per-stage rule can give the partition a negative gain from a pure source. A partition tag that holds no water in that cell then ends the step below zero. Section 11.2 gives only the size of the miss, not its sign, and no test covers the stage split.

**Failure scenario.** With ARS343, the model default (CTS b_exp = [0, 1.2085, -0.6444, 0.4359], c = [0, 0.4359, 0.7179, 1]): one bracketed gain G lifts a parent from P_n = -s*G*dt with s in (0.436, 0.718]. Only stages 3 and 4 see a parent >= 0, so every partition tag gets M_k*(b3+b4)*G*dt = -0.2085*M_k*G*dt. A tag that holds 0 ends at -0.2085*G*dt. On main it ends at +G*dt, and the target gains (1-s)*G*dt. With ARS222, the validation's tableau (b = [-0.7071, 1.7071, 0]): the parent is >= 0 at stage 1 (U_n) and < 0 at stage 2 because of another process's loss (implicit transport, or another bracket), and the forcing adds G > 0. The partition then gets delta*G*dt = -0.7071*M_k*G*dt. Also with ARS222, a parent that is a rounding amount below zero at the step's start (-1e-30) gives the partition 1.7071*G*dt, while +0.0 or -0.0 gives exactly G*dt. That is a jump at zero, and it makes 11.2's 'mean zero' depend on crossing points being spread evenly through the step. The negative tag values then go to the partition repair (led_fix, which V5 scores) or to q_tag_res.

**Evidence.** Checked by computation (Python 3.12, tableaux copied from ClimaTimeSteppers src/solvers/imex_tableaus.jl in the depot). A scalar IMEX-ARK loop, explicit part only, applied the kernel's rule per stage (gain = 0 if P_i < 0 else max(D,0); loss share = clamp(tag/P) if P > 0 else 0). Crossing up with ARS343: s = 0.5 and s = 0.6 give tag_k = -0.2085 under TargetGain and 1.0 under ParentGain. Crossing down with ARS222 (P0 = 0.05 or 0.2, gain 1, unbracketed loss 3): tag_k = -0.7071 under TargetGain and 1.0 under ParentGain. The same script confirms 11.2's table: ARS222 overclaim 1.00, shortfall 0.71; ARS343 overclaim 0.44, shortfall 0.77; mean over the crossing point 0 (sum b_i c_i = 1/2 for both). Checked by reading: tagged_water.jl:356-357 (the rule), :549 (the parent is read from the stage state Y), :661-663 (M_k * gain, not bounded by the tag's holdings). The only tests of the rule are scalar or one Euler step (test/tagged_water_tests.jl, new testset). None integrates a tableau. Fix: state the sign reversal and the ARS222 jump at zero in 11.2 and in question 2 of 11.10. Add a unit test that runs one ARS222 step and one ARS343 step on a scalar column through _accumulate_water_tags! and pins -0.2085, -0.7071 and 1.7071. If the owner wants the partition's gain kept in [0, G], one option is to read the sign once per step, from the parent at the step's start. That needs a tags-only cache field and gives up the zero mean.

**Verifier.** I reproduced it with the tableaux from the depot (ClimaTimeSteppers ZxgOv imex_tableaus.jl). ARS343 has b_exp = [0, 1.2085, -0.6444, 0.4359] and c = [0, 0.4359, 0.7179, 1]. ARS222 has b = [-0.7071, 1.7071, 0] and c = [0, 0.2929, 1]. I ran the per-stage rule of tagged_water.jl:356-357, reading the stage parent (:549) and applying it by mask (:662). ARS343 with P_n = -0.5 or -0.6 of G*dt gives the partition -0.2085*G*dt; ParentGain gives 1.0. ARS222 with P_n = -1e-30 gives 1.7071; with +0.0 or -0.0 it gives 1.0. ARS222 crossing down (P0 = 0.05 or 0.2, loss 3) gives -0.7071. These fit 11.2's bounds: ARS343's shortfall of 0.77 = (1 - 0.436) + 0.2085. So the size is covered. What 11.1 and 11.2 never say is the sign. 11.1 says the tags 'do not change' below zero, and 11.2 says those stages give the gain 'to the negative part'. A reader would expect the partition's gain to lie in [0, G*dt]. It does not: a pure source can drive a partition tag that holds 0 below zero, which main cannot do. That feeds led_fix and the repair that V5 scores. No test integrates a tableau. This bears on owner question 2. It is a gap in the design text, not a mismatch between code and spec.

## kernel-2 (CONFIRMED, minor)

`NEWS.md:6`

**Claim.** NEWS says 'the tags are unchanged bit for bit wherever the parent is never negative', read cell by cell. The code gives that only in a run whose parent is never negative anywhere. Validation rule V3 in design 11.7 (line 899) makes the same cell-by-cell claim.

**Failure scenario.** One cell k of a column has rho q_tot < 0 for one stage while the forcing moistens it. TargetGain gives the partition tags 0 there, and main gives M*G. The tag fields now differ in cell k. At the next step, vertical advection, EDMF fluxes and diffusion of rho q_tag_* move that difference into cells k-1 and k+1, whose parent was never negative. So the claim in NEWS is false. V3's fallback clause ('different only in cells and after times where the untagged twin's parent was ever negative') would fail at site 26 even with correct code if its parent ever went below zero in a single cell.

**Evidence.** Checked by reading only. The kernel's per-evaluation statement (tagged_water.jl:345-348, the docstring of water_tag_target_gain) is correct. The rho q_tag_* fields are transported tracers, so a difference in one cell does not stay there. docs/known_issues.md words it correctly: 'The tags change only once the parent has gone below zero somewhere.' Fix: in NEWS, write 'in a run whose parent (the non-precipitating water under water_tag_precipitation) is never negative'. For V3, compare by column and time, from the first time the parent is negative anywhere in the column, and ask the owner before changing a pre-registered rule.

**Verifier.** NEWS.md:6 says 'the tags are unchanged bit for bit wherever the parent is never negative'. Read as 'in every cell', that is false. The rule changes the partition tags in a cell with parent < 0 (tagged_water.jl:662). The ρq_tag_* fields are transported, by tracer advection or through the follower's shares, so the difference reaches cells whose parent was never negative. The 30-day parity record shows tags differing at many levels from day 11.5, for example q_tag_pbl at 435 m. known_issues.md:372-373 has the correct run-level wording ('once the parent has gone below zero somewhere'). V3's fallback clause has the same cell-by-cell weakness, but its primary pass rule (bit for bit at site 26) is unaffected. Wording only. No code defect.
